# Цифровой управляющий · настоящий ИИ и границы самостоятельности

Обновлено: 12 октября 2026.

## Что работает сейчас

- `app/business-brain.js`: локальные объяснения положения дел на основании **только внесённых владельцем записей**. Это правила, а не подключённая модель.
- `app/sales.js` → `getBusinessSnapshot()`: агрегированные обращения, этапы, покупки и ручные рекламные расходы без имён и контактов.
- `app/initiative.js`: после отдельного согласия заранее готовит локальные черновики клиентам. Пока приложение открыто, наблюдает за сохранёнными изменениями, по которым может работать. Отправки и денежных операций нет.
- Плазма отвечает на вопросы «Как дела?», «Что с продажами?», «Что ты успел?», «Как реклама?», «Что с деньгами?» по реальным локальным записям. При отсутствии данных честно об этом говорит.
- Никаких выдуманных «ИИ подключён», «отправил клиенту», «прибыль выросла», «сам зарабатывает».

## Задел под настоящую модель

`server/manager-model.mjs` — **только серверный адаптер**, который можно позже вызвать из защищённого бэкенда. Он проверяет переданное сервером согласие, отбирает агрегированные показатели и выполняет текстовый запрос к OpenAI Responses API со `store:false` и без инструментов для внешних действий.

Этот файл **не развёрнут и не является общедоступным HTTP-маршрутом**. Пока нельзя обращаться к модели из приложения. Сайт на GitHub Pages сам по себе не исполняет серверный JavaScript.

Для запуска реального ИИ потребуются:

1. Выбранный серверный хостинг и работающая аутентификация пользователей.
2. **Серверная** проверка личности и хранимого разрешения `aiAnalysis`. **Нельзя** принимать `consent: true` от любого посетителя и считать это аутентификацией.
3. Секреты `OPENAI_API_KEY` и `OPENAI_MODEL` только в переменных окружения на сервере — никогда в `app/`, публичном JavaScript, HTML, GitHub или `localStorage`.
4. Лимиты на число вызовов, защищённый журнал, контроль расходов на модель, тайм-ауты, журнал ошибок без персональных данных.
5. Явное предупреждение владельца о том, какие агрегированные данные будут отправлены провайдеру, и возможность отозвать согласие.
6. Только после готовой серверной защиты — отдельный авторизованный API-маршрут, который вызывает адаптер. Клиент получает ответ, а не ключ.
7. Отдельные разрешения и безопасные интеграции для переписки, рекламы, банков, договоров. Одобрение аналитики **не** даёт полномочий что-либо отправлять, покупать или менять.

Пример **внутреннего** вызова из доверенного, авторизованного серверного обработчика:

```js
import {askManagerOnServer} from './manager-model.mjs';

// snapshot — агрегаты, собранные по записям подтверждённого пользователя.
// consent — состояние разрешения из серверной базы, НЕ из произвольного тела HTTP-запроса.
const result = await askManagerOnServer({
  question: verifiedQuestion,
  snapshot: verifiedSnapshot,
  consent: verifiedServerSideConsent
});
```

Интерфейс `askManagerOnServer()` возвращает текст и явную пометку `externalActions: 0`. Он **не умеет** исполнять или разрешать внешние действия.

Официальная документация: https://developers.openai.com/api/reference/resources/responses/methods/create

## Следующий рабочий маршрут

Самый полезный следующий реальный канал — одно подключение новых клиентских сообщений с ограниченными правами, при наличии подходящего API и согласия владельца. Сначала только чтение, затем черновики, затем отдельно согласованная отправка в рамках конкретных правил. События должны подтверждаться источником; список «в работе» не равен успешно обработанным обращениям. Закрытие приложения не должно создавать иллюзию продолжающейся фоновой работы.

Задача продукта — **снизить количество действий человека**, а не добавить ещё десять настроек. Главным интерфейсом остаётся существующая плазма, а журнал открывается по необходимости.
