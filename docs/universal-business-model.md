# «Цифровой управляющий» — один управляющий для любого масштаба и направления

Решение продукта: 12 октября 2026.

## Базовый принцип

Продукт **не является CRM только для продаж**. Его назначение — самостоятельно вести разрешённые процессы бизнеса любого размера: от одиночного цветочного магазина до сети филиалов, завода, проектной команды и группы компаний. Продажи — первая уже работающая область данных, **не ограничение архитектуры**.

Не следует делать отдельные приложения для розницы, услуг, торговли, производства. Один управляющий собирает индивидуальную картину бизнеса из общих процессов и подключённых возможностей.

**Один вопрос для старта:** «Чем живёт твой бизнес?» Пример ответа: «У меня цветочный магазин, собираем букеты на заказ и доставляем по городу». Из этого описания управляющий может предложить обратить внимание на заказы, остатки, списания, доставку, повторные покупки. Ответ — заявление пользователя, **не доказательство реального состояния бизнеса**. Человек может описать и смешанный бизнес.

## Универсальные сущности будущей системы

Не привязывать базовые сущности к слову «продажа». Модель должна уметь представлять:

- **Организация**: один предприниматель, несколько направлений, подразделения, филиалы, роли и полномочия.
- **Контакт и партнёр**: клиент, поставщик, сотрудник, подрядчик и другие стороны.
- **Обращение / потребность**: интерес, заказ, запись, запрос расчёта, жалоба, внутреннее событие.
- **Обязательство и результат**: товар передан, услуга оказана, работа выполнена, заказ отгружен, проект сдан; никаких завершений без подтверждённого события.
- **Ресурсы**: товары, материалы, запасы, техника, рабочие места, сотрудники, время, бюджеты.
- **Процесс и правила**: этапы, сроки, ответственные, допустимые самостоятельные действия.
- **Деньги**: расчёт, счёт, платёж, закупка, возврат и *проверенный* результат; не путать выручку с прибылью и суммы заказов с полученными деньгами.
- **Событие и факт**: источник, время, достоверность, разрешение на чтение, история изменений.
- **Поручение и решение управляющего**: задача, план, выполненный шаг, полученный результат, ограничения и возможности отмены.

## Компоновка навыков (пример, не исчерпывающий справочник)

| Компания | Какие процессы уместны | Чего нельзя изображать без подключения |
| --- | --- | --- |
| Цветочная лавка | Остатки и свежесть, списания, поставщики, букеты на заказ, доставка, сезонность | Остатки и реальные продажи из кассы |
| Салон, мастерская, клиника | Записи, график, занятость специалистов, услуги, качество, повторные клиенты | Медицинские решения, записи и расписания без данных или разрешений |
| Эвакуатор, курьеры | Входящие заявки, маршруты, время отклика, загрузка транспорта, затраты | Вызовы и маршруты без подключённой связи/геоданных |
| Завод | Смены, производственные задания, материалы, брак, срок, себестоимость | Загрузка станков или качество выпуска без датчиков и учёта |
| Стройка, агентство | Проекты, этапы, подрядчики, бюджет и согласования | Фактическое выполнение этапа без подтверждения |
| Сеть компаний | Филиалы, роли, сводные показатели, отклонения по точкам, единые процессы | Придуманные показатели отсутствующих подразделений |

## Масштабирование без «тысячи кнопок»

Малому бизнесу нужен **один управляющий и короткая история действий**. Для среднего и крупного бизнеса ему необходимы роли, разные команды/направления, права, аудит, безопасная интеграция со множеством систем, очереди задач, надёжный сервер и разграничение доступа.

Сложность внутри, а не на первом экране. По умолчанию управляющий рассказывает, что увидел, что сделал, какую возможность нашёл, а что нужно согласовать. Глубокие отчёты — по запросу. В интерфейсе главный герой — утверждённая плазма.

## Текущее состояние кода (честно)

- `app/business-context.js` — локальное произвольное описание бизнеса и **необязательные подсказки по ключевым словам**, учитывающие смешанные направления. Это не ИИ и не исчерпывающая классификация отраслей.
- `app/business-brain.js` — локальные ответы по описанию и **имеющимся ручным данным «Продаж»**. Без подключённых источников нельзя утверждать, что система знает остатки, занятость, производство или документы.
- `app/initiative.js` — первый пример самостоятельного действия: подготовка черновиков по ручным обращениям **после согласия пользователя**. Не звонит, не отправляет сообщений и не исполняет банковские операции.
- `app/sales.js` и `app/task-journal.js` — действующие частные модули, со временем должны подключаться к универсальной модели как адаптеры, без потери старых записей.

## Следующий инженерный порядок

1. Объединить обращение, заказ, запись, услугу и работу через универсальную сущность **рабочего события**, оставив старые данные без миграции до её тестирования.
2. Добавлять адаптеры видов деятельности: расписание/запись, товар/остаток, производство/заказ, филиал/сотрудник. Начинать с одного реального источника на конкретном пилотном бизнесе.
3. Правила самостоятельных действий устанавливать по типу действия и роли, **не по названию отрасли**. Никаких скрытых платежей, подписаний или массовых отправок.
4. Реальная модель ИИ анализирует только разрешённые данные через защищённый сервер; проверенные события отделяются от догадок.
5. Критерий качества — не число меню, а сколько реальной проверяемой рутины управляющий снял с владельца без новых рисков.

## Реализованная общая модель событий (12 октября 2026)

- `app/workflow-core.js` создаёт **единый, исключительно читающий** срез доступных рабочих объектов из установленных адаптеров; старые записи **не мигрируются и не изменяются**.
- Текущие адаптеры: `Продажи` → обращения; `Мои дела` → личные обязательства; `Поручения` → подтверждённые передачи дел управляющему. Демонстрационные планы не считаются реальными поручениями.
- В нормализованной записи есть тип процесса (`kind`), этап (`state`), ответственный (`owner`), источник (`source`), время и срок, где эти сведения действительно известны. **Переданное дело и соответствующее поручение считаются одним обязательством**, не удваивая нагрузку.
- Адаптеры допускают будущие домены (`booking`, `stock`, `production`, `service-job`, `branch`) без жёсткого списка отраслей. Это **только архитектурная возможность**, такие источники пока не подключены.
- `app/task-journal.js` теперь экспортирует `getWorkSnapshot()`, а обновления сохранённых задач сообщают событием `dm:journal-changed`. `app/business-brain.js` учитывает срочные и просроченные дела наряду с обращениями; `app/initiative.js` показывает их в уже существующем отчёте.
- Нет серверной фоновой работы, автоматической отправки, платежей или контроля производства. Подготовленный текст не считается выполненным поручением. Согласие пользователя на подготовку ответов не распространяется на сторонние сервисы.
